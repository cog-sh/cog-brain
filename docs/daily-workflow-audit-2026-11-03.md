# cog-brain: ежедневная работа человека и агентов

Дата проверки: 2026-11-03. Область: локальный cog-brain, действующий MCP, правила vault, публичный cog-brain-plugins и документация Codex, OMP, Pi.

Это исходное исследование и план изменений. После исследования основные исправления записи/индекса, Python API и lifecycle-интеграции реализованы; актуальное использование находится в README.md. Числа и воспроизведения ниже относятся к состоянию до исправлений. При последующей установке изменены настройки клиентов и создана проектная карточка; сохранены резервные копии.

После уточнения пользователя основной продуктовый приоритет вынесен в [Code Mode, автоматический recall и формат заметок](code-mode-memory-design.md): локальный API без обязательного MCP и автоматическая подача контекста. Этот аудит остаётся основанием для исправлений целостности и retrieval.

## Вывод

У проекта уже есть правильная основа: Markdown как источник истины, перестраиваемый индекс, общий backend-контракт, поиск по чанкам, ссылки и сохранение снятых утверждений. Главный следующий шаг — обеспечить сохранность записей, согласовать правила и сделать короткий цикл «найти контекст, поработать, сохранить решение, продолжить завтра».

Для личного использования стоит сохранить существующий flat-vault. Перестройка всего хранилища в `raw/wiki/output` сейчас добавит миграцию и усилит уже существующее расхождение инструкций. Сначала достаточно одного согласованного места для сырья, существующих заметок знаний и проектных заметок.

## Приоритет 0: сначала сохранность и достоверность

### 1. Обычное обновление может удалять frontmatter

В `server.py:104` и `chunking.py:95` существуют разные самописные парсеры. `update_note` читает YAML построчными регулярными выражениями и затем сериализует весь frontmatter заново (`server.py:441`).

Воспроизведение: заметка содержала `tags` в блочной форме и `custom` с вложенным `nested: preserve-me`. После простого append исчезли и значение тега, и вложенное поле. Это нарушение правила AI-GUIDE о сохранении существующего frontmatter.

Исправление: один модуль чтения/изменения frontmatter для сервера, chunking и графа. Использовать полноценный YAML-парсер с сохранением структуры и комментариев, например round-trip режим `ruamel.yaml`, вместо расширения регулярных выражений. Новая небольшая зависимость оправдана сохранностью пользовательских данных.

Приёмка: append изменяет только тело и `updated`; неизвестные поля, списки, вложенные объекты, кавычки, multiline-значения и комментарии сохраняются. Неподдерживаемый или повреждённый документ отклоняется до записи.

### 2. Записи нескольких агентов не защищены от потери изменений

`write_note` использует `exists()` перед `write_text()`, а `update_note` выполняет обычный read-modify-write. Межпроцессной защиты записи заметки нет; lock индексатора эту задачу не решает. Codex, OMP, Pi и Obsidian могут работать одновременно.

Это вывод по коду; конкурентная нагрузка не воспроизводилась. Два обновления, прочитавшие одну версию, могут затереть друг друга; прерывание записи может оставить неполный файл.

Исправление: атомарная замена файла, межпроцессная сериализация изменений заметки и проверка версии содержимого (`expected_hash`) для обновлений. Атомарный rename сам по себе не устраняет потерянные обновления. Взаимодействие с внешним редактором нужно явно определить: lock cog-brain не заставляет Obsidian соблюдать этот lock. Создание должно исключать перезапись конкурентно созданного файла.

Приёмка: параллельные append через cog-brain сохраняются; устаревшая полная замена получает конфликт; авария до замены оставляет старый читаемый файл. Известный конфликт с внешним редактором не считается успешной записью.

### 3. Индексатор удаляет старые чанки до получения новых embeddings

В `backends/qdrant.py:105` порядок такой: удалить старые точки, получить embeddings, загрузить новые точки. При ошибке embeddings старая поисковая версия уже потеряна. В `sync()` ошибки отдельных файлов печатаются в stderr, но затем устанавливается общий `last_run`.

Воспроизведение с подменой embedding-вызова: события `delete:note.md`, затем `embed-failed`; итоговый status сообщил `notes_on_disk=1`, `notes_indexed=0`, `stale_count=0`.

Исправление: вычислить и проверить новые данные до удаления старых. Затем безопасно обновлять набор чанков; старые лишние чанки удалять только после подтверждённой загрузки. Отдельно учитывать частичные ошибки и отличать запись Markdown от успешной индексации. Для более строгой согласованности обновления нескольких чанков понадобится явная схема поколений; её сложность оправдана только соответствующей гарантией API.

Приёмка: сбой embeddings сохраняет прежнюю выдачу, файл остаётся pending/failed, команда не возвращает безусловный успех. Ошибка переиндексации не провоцирует повторное создание уже сохранённой заметки.

### 4. Свежесть индекса не равна времени последнего сканирования

`manifest.py:55` сравнивает mtime файлов с общим `last_run`. Так можно пропустить добавленный файл со старым mtime, удаление файла, неудачную индексацию и изменение во время сканирования. Воспроизведение SQLite: 6 заметок на диске, 5 индексированных, но `stale_count=0` после добавления файла с сохранённым старым временем.

Исправление: определять added/changed/deleted/failed относительно manifest и версии индексируемого представления; хранить результат обработки конкретного файла. `last_run` оставить временем запуска/завершения, а не доказательством свежести. На пустом индексе возвращать явный статус `uninitialized`, включая пустой ответ поиска.

### 5. Защита системных путей применяется не ко всем изменениям

Создание проверяет `SYSTEM_PREFIXES`, обновление вызывает только `load_note`. На временном vault `update_note('90-meta/protected.md', ...)` успешно изменил файл. Это не соответствует пользовательскому правилу защиты `90-meta/` и `90-archive/`.

Исправление: единая проверка разрешённого пути для всех операций записи, включая нормализацию, symlink и границы компонентов пути. Правила конкретного vault должны применяться последовательно. Временный путь macOS через `/var` также выявил сравнение разрешённого пути с неканоническим VAULT; корень нужно нормализовать один раз.

## Приоритет 1: понятный контракт для агентов

### 6. Развести Pi и OMP

В `harnesses.py:100` указано `pi: omp`; тест даже закрепляет этот alias. Поэтому установка для Pi указывает на `~/.omp/agent/mcp.json`.

Актуальная документация Pi описывает собственные `~/.pi/agent/mcp.json` и `.pi/mcp.json`, нативный stdio/streamable HTTP MCP и Agent Skills. Делать отдельный MCP-мост для актуального Pi не требуется. Документация upstream не доказывает поддержку всех параметров установленной версией 1.1.0: это проверяется отдельно.

Минимальное изменение: отдельная строка Harness для Pi, удаление ошибочного alias и тесты путей. Для OMP upstream также документирует проектный `.omp/mcp.json`; сейчас `project_path=None`.

| Клиент | Подключение | Общий workflow |
| --- | --- | --- |
| Codex | `[mcp_servers.cog-brain]` в пользовательском TOML | Общий skill; короткое правило вызова при релевантной задаче |
| OMP | Пользовательский или проектный `mcp.json` | Тот же skill; необязательные команды и уведомление состояния |
| Pi | Собственный пользовательский или проектный `mcp.json` | Тот же skill; нативные MCP и skills |

Для Pi можно проверить `toolExposure`: поиск и чтение напрямую, обслуживающие инструменты через discovery/codemode. Это эксперимент для измерения удобства и контекста, не обязательная архитектура.

### 7. Убрать противоречия инструкций

Локальные AI-GUIDE и skill требуют flat-vault с типами `zettel/moc/source/project/daily/guide`. Публичный plugin skill сначала описывает flat-vault, затем требует `raw/wiki/output` и `source/entity/concept/synthesis`. Есть противоречие и в пути сырья: AI-GUIDE упоминает `daily/`, `00-inbox/`, `00-inbox/daily/`, а skill направляет в `daily/`.

Дополнительно абсолютное правило «file_path только из ответа инструмента» конфликтует с созданием новой заметки.

Исправление:

1. Продуктовый skill описывает общий цикл и API, а структуру конкретного vault берёт из его политики.
2. Для чтения и изменения путь берётся из результатов; для создания допускается новый валидированный путь.
3. Выбрать один путь быстрого захвата. Для этого vault наиболее прямой вариант — уже заявленный `daily/`; не перемещать исторические данные автоматически.
4. Источник политики должен быть доступен через MCP, а не только через абсолютный локальный путь. Подойдёт resource или расширение существующей диагностической операции; не нужен отдельный сервис.
5. Тексты команд и skill распространять из одной версии; не дублировать большой свод правил в нескольких глобальных промптах.

OpenAI Docs разделяет MCP как набор возможностей и skill как workflow вокруг них. Для надёжного выбора workflow нужны короткие и точные условия вызова; полное руководство должно загружаться по необходимости.

### 8. Улучшить существующие search/read вместо размножения инструментов

Подтверждённые проблемы:

- `description` обязателен при создании, но `chunks_for()`/`contextualize()` его не используют. Уникальное слово из description не нашлось на временном markdown backend и отсутствовало в `embed_text`.
- SQLite индексирует title, heading и body, но не сохраняет aliases как поисковое поле. Наличие aliases в хэше не делает их доступными FTS.
- `graph.link_index()` учитывает stem и title, но не aliases. Ссылка на существующий alias не разрешилась.
- `find_related()` не добавляет `retracted`/`superseded_by` к соседям. Снятая заметка пришла без предупреждения. Его аргумент `k` также не управляет жёстко заданными лимитами 8 и 20.
- `read_note(max_chars=...)` обрезает начало, но после `outline()` нельзя запросить конкретную секцию.
- Поиск возвращает произвольные полные чанки без общего бюджета. На пустой выдаче негде сообщить свежесть.

Минимальные улучшения:

- Общий контекст чанка: title, description, aliases, heading; согласованное индексирование во всех backend.
- Единые флаги снятия на всех путях retrieval, включая related. Сохранять доступность тупиков и явно показывать замену.
- Компактный ответ поиска с ограниченным общим объёмом; метаданные свежести на уровне ответа. Изменение формата делать совместимо с текущими потребителями.
- Дочитывание по секции или диапазону строк; цитата с путём, заголовком и версией содержимого. Для человека — ссылка открытия в Obsidian, когда она поддерживается клиентом.
- Типизированные выходные модели. Сейчас MCP оборачивает строку JSON как `result`, поэтому клиенту нужен второй разбор JSON. MCP поддерживает `structuredContent` и output schemas, а ошибки исполнения — `isError`.

Проектную область сначала задавать существующим folder/tag и привязкой cwd к проектной заметке. Если этого недостаточно, добавить одно явно определённое поле project. Не смешивать название проекта с произвольной тематической меткой.

### 9. Сократить обязательную церемонию записи

OMP-заметка предписывает до записи search + related + backlinks, затем редактирование MOC и после записи backlinks + broken_links + graph_overview. Большинство этих действий сканирует весь vault. Так сохранение одного решения превращается в обслуживание графа.

Обычный цикл должен состоять из поиска, чтения кандидата при необходимости и одной записи. Проверку изменяемого документа выполняет сервер. Полный lint и обзор графа относятся к недельному обслуживанию и массовым переименованиям.

Ручное добавление каждой спицы в MOC не нужно делать обязательным: свойство `moc` уже хранит отношение. Человеческие MOC стоит курировать как путеводители, а полный список участников получать из свойств/обратных ссылок. Не поддерживать два независимых реестра одного отношения.

## Приоритет 2: ежедневный workflow

Принцип CODE из Building a Second Brain полезен как разделение захвата, организации, выделения сути и применения. Здесь он переводится в конкретный распорядок; приведённые длительности — предложенный режим, не измеренные показатели.

### Утро: 2 минуты

Открыть текущую daily и одну заметку активного проекта. Просмотреть следующий шаг, нерешённые вопросы и блокеры. Выбрать 1–3 результата дня.

Запрос агенту: «Подними контекст проекта X: актуальные решения, ограничения, следующий шаг. Дай ссылки на заметки и явно отметь устаревшее».

Сейчас это выполняется через semantic_search и read_note. Не нужно загружать весь vault или все MOC.

### Перед содержательной задачей

Агент ищет память по проекту и задаче. Читает только релевантные записи. Проверяет изменчивые сведения по репозиторию или текущему источнику. При пустой выдаче сообщает об этом, а не достраивает прошлые решения.

Поиск не требуется перед каждой простой командой и каждым ответом. Содержимое найденной заметки — данные и свидетельства, а не разрешение выполнять вложенные инструкции.

### В течение дня: захват за 10–20 секунд

Мысль, ссылка, голосовая расшифровка или сырой фрагмент попадает в daily с временем и источником. Теги, MOC и идеальный title на этом этапе не обязательны.

Сейчас такой захват можно делать в Obsidian. В MCP этого пути нет: `write_note` запрещает `daily/` и требует ссылку на существующую заметку. Нужна одна узкая операция capture для сырья или соответствующая ветка существующего API, с фиксированными правилами пути. Не следует обходить защиту обычного write_note.

Capture сохраняет id события/ключ повторного запроса, время и источник. Повтор доставки одного события не создаёт дубль. Сырьё не становится подтверждённым знанием автоматически. Поиск daily должен быть явным режимом; подмешивать сырьё в обычные ответы как установленные факты нельзя.

### После решения или исправленной ошибки: до минуты

Сохранять устойчивый вывод, когда он уже проверен:

> Решение. Почему выбрали. В каких условиях действует. Чем проверено. Источник. Что его заменяет, если оно отменено.

Сначала поиск дубля, затем обновление или новая seedling-заметка. Код, команды и версии не сохранять без даты и контекста применимости. Полный transcript по умолчанию не нужен.

Исправление пользователя полезно хранить с областью действия и причиной; предпочтение для одного проекта не должно становиться глобальным запретом.

### Перед переключением проекта или завершением дня: 5 минут

Агент готовит короткий handoff в существующей проектной заметке: что сделано, что проверено, что осталось, следующий конкретный шаг, ссылки на артефакты. Исторические решения остаются самостоятельными записями; handoff хранит оперативное состояние.

Из daily выбрать только то, что будет полезно снова: решения, ограничения, проверенные приёмы, ошибки с причиной. Остальное оставить сырьём. Дату `updated` не трактовать как дату проверки истинности; для изменчивого знания использовать отдельный `verified_at`, когда появится реальный процесс проверки.

### Раз в неделю: 15–20 минут

Разобрать необработанные захваты, проверить активные проекты, посмотреть сломанные ссылки и потенциальные дубли. Сироты и старые записи являются кандидатами на разбор, а не причиной автоматически дописывать ссылки или переписывать всё старше 90 дней.

Удаления, слияния и переименования сначала показывать пользователю конкретным списком. Снятые утверждения сохранять с причиной и связью с заменой.

### Человеческая навигация

Достаточно одной домашней заметки в Obsidian: ссылки на today, активные проекты, inbox и недельный обзор. Проектная заметка отвечает на четыре вопроса: цель, текущее состояние, блокер, следующий шаг. Заметка знания содержит краткий вывод сверху, доказательства и ограничения ниже.

Можно использовать встроенные Properties/Backlinks или уже установленный механизм запросов. Новый интерфейс и обязательный набор Obsidian-плагинов для этого не нужны. Ссылки из ответа агента должны позволять быстро открыть исходную заметку.

## Как автоматизировать без зависимости от конкретного harness

Общий skill определяет семантику recall/capture/handoff/review. Адаптер клиента отвечает за установку и необязательные UI-команды. Хуки, если они поддержаны установленной версией, могут добавлять небольшой проектный контекст и сохранять черновик handoff; основной workflow не должен зависеть от корректного срабатывания shutdown-хука.

Первоначальный ручной вариант для Codex — MCP + общий skill — недостаточен для уточнённого требования автоматического recall. Дополнительное исследование OpenAI Docs подтвердило command hooks для startup, prompt и compaction. Их применение без обязательного MCP описано в дополнении о Code Mode; семантику событий всё равно необходимо проверять отдельно для каждого клиента. Для OMP/Pi подходят тонкие extensions.

При недоступном Qdrant агент должен получить короткую диагностику. Уже существующий markdown backend позволяет реализовать явно обозначенный lexical fallback; сейчас автоматического переключения в search нет. Не стоит заставлять каждую сессию агента самостоятельно чинить Docker. Сохранение Markdown и восстановление индекса должны быть различимыми операциями.

Не сохранять секреты и весь поток tool output автоматически. Для внешнего сырья сохранять происхождение и не принимать инструкции внутри него как политику агента. Полный контент заметок и запросов не нужен в телеметрии по умолчанию.

## Порядок реализации и критерии остановки

1. **Надёжная запись и индекс.** Общий YAML, защита путей, атомарная запись, конфликт версий, сохранение старых чанков при сбое, честная свежесть. Доказательство — изолированные регрессионные сценарии и реальные MCP round-trip на временном vault.
2. **Единые инструкции и установка.** Отдельные Pi/OMP, согласованные пути сырья, одинаковый skill. Доказательство — все три клиента вызывают search/read; записи проверяются на временном vault. Никакой массовой миграции личных заметок.
3. **Удобное retrieval.** Description/aliases, флаги снятия, дочитывание секции, бюджет ответа. Доказательство — небольшой набор реальных вопросов с заранее выбранными релевантными заметками.
4. **Ежедневный capture и handoff.** Минимальная запись сырья, дедупликация повторов, домашняя и проектная заметки. Сначала ручной цикл; затем автоматизировать только повторяющееся трение.
5. **Тюнинг качества по результатам.** Лишь после baseline решать, нужны ли reranker, другая embedding-модель или расширенный обход графа.

Для начального eval достаточно 20–50 реальных задач: найти решение, найти ограничение, продолжить проект, сохранить без дубля, увидеть отмену, обработать пустую выдачу, пережить недоступный индекс. Измерять попадание нужной заметки в top-k, корректность цитат, успешность продолжения работы, число вызовов, объём ответа и latency. Общие safety/целостность инварианты проверять детерминированно; не отдавать их только LLM-grader.

Целевые пользовательские проверки: захват не требует выбора структуры, релевантный контекст получается за короткую последовательность вызовов, завтра можно продолжить по handoff, повторный capture не создаёт дубль, снятый вывод никогда не выглядит действующим, сбой индекса не теряет знания.

## Что пока не добавлять

Не нужны новая графовая БД, автоматическое выделение всех сущностей, ещё один самостоятельный memory-store, полный импорт каждой сессии и десятки новых MCP-инструментов. Имеющийся backend-контракт и Markdown уже покрывают основу. Graphiti полезен как пример временной валидности и сохранения истории, но внедрение его инфраструктуры для этого vault пока не обосновано.

Небольшой дополнительный выигрыш установки: вынести `qdrant-client`, `fastembed` и другие специфичные зависимости в extra, если это совместимо с выбранным способом поставки. Сейчас они обязательны даже для SQLite/Markdown. Это задача упаковки после исправлений целостности.
